# ADR-001 Модульный монолит для мессенджера для владельцев животных ЛапаЧат

**Статус:** принято для учебного проекта.  
**Дата:** 5 октября 2026 года.

## Контекст

Проект продолжает тему первой лабораторной работы о мессенджерах. Предлагается собственная система; внутреннее устройство Strim по отзывам установить нельзя. Цель первой версии — карточки питомцев, поиск владельцев животных по городу и виду питомца, личные и тематические групповые чаты, текстовые сообщения и отметки прочтения.

Учебные допущения: три разработчика, восемь недель на первую версию, до 1000 зарегистрированных пользователей, до 100 пользователей одновременно и 20 отправок сообщений в секунду. С учётом опроса активных чатов предполагается до 100 HTTP-запросов в секунду. Это исходные условия проектирования, а не статистика реального сервиса. Бюджет ограничен; отдельной команды эксплуатации нет. Сервер и база предполагаются в дата-центре РФ.

## Критерии и альтернативы

| Критерий | Обычный монолит | Модульный монолит | Микросервисы | Serverless |
|---|---|---|---|---|
| Срок запуска | Короткий, но границы кода не закреплены | Небольшие затраты на границы модулей | Нужны сеть, отдельные релизы и наблюдение сервисов | Быстрый старт отдельных функций; ядро переписки требует дополнительных решений |
| Масштабирование | Всё приложение вместе | Всё приложение вместе; модули можно выделить позже | Отдельные сервисы | Отдельные функции, с ограничениями платформы |
| Работа с данными | Общая транзакция | Общая транзакция с контролем доступа к таблицам | Транзакции между сервисами усложняются | Зависит от выбранного хранилища |
| Стоимость сопровождения | Низкая сначала; может расти из-за связанности | Приемлема для трёх разработчиков | Слишком велика для заданной команды | Зависит от числа вызовов; частый опрос увеличивает их количество |
| Риск для проекта | Связанный код затруднит изменения | Нужна дисциплина границ | Сложность распределённой системы до появления потребности | Зависимость от провайдера и возможные задержки запуска |

Оценки качественные и относятся к выбранному контексту. Размер команды сам по себе не определяет архитектуру. Решение опирается на подход лекции: сначала ограничения, затем архитектурный стиль.

## Решение

Использовать веб-клиент React и TypeScript, один сервер Python и FastAPI, одну PostgreSQL. Эти технологии указаны как проектный выбор; приложение в данной лабораторной работе не реализуется. Внутри сервера выделить:

1. **Учётные записи:** пользователи, карточки питомцев, одноразовые коды, сессии.
2. **Переписка:** чаты, участники, сообщения, отметки прочтения.
3. **Адаптеры SMS:** два взаимозаменяемых подключения к внешним поставщикам.

Модуль переписки получает сведения о пользователе через публичный интерфейс модуля учётных записей. Прямой доступ к чужим таблицам из прикладного кода запрещён. Проверки зависимостей должны закрепить это правило при реализации. Ссылки между таблицами внутри общей БД сохраняют целостность данных и не отменяют границы кода.

В первой версии новые сообщения получаются обычным HTTP-опросом раз в три секунды в активном чате. Так весь API можно описать в OpenAPI без отдельного протокола WebSocket. Неотправленные сообщения сохраняются в IndexedDB браузера. Повторная отправка использует прежний clientMessageId; сервер возвращает исходное сообщение вместо создания копии. IndexedDB защищает от обычного разрыва связи и перезапуска вкладки, но не от очистки данных браузера или поломки устройства.

## Последствия и риски

Плюсы: один серверный релиз, простая локальная транзакция, меньше инфраструктуры и понятные границы ответственности. Минусы: сервер обновляется целиком; ошибка процесса влияет на все серверные функции; база остаётся общей точкой отказа; опрос создаёт лишние HTTP-запросы.

| Риск | Мера | Остаточное ограничение |
|---|---|---|
| SMS не отправляется | Тайм-аут 5 секунд, резервный провайдер, общий предел 15 секунд | Принятие SMS провайдером ещё не означает доставку на телефон |
| Потерян ответ на отправку | Локальная очередь и уникальный clientMessageId | Сообщение нужно сохранить локально до сетевого запроса |
| Общий сервер или БД недоступны | Контроль доступности, резервные копии, проверка восстановления | Первая версия не обещает непрерывную доступность при аварии узла |
| Модули начинают обращаться к чужим таблицам | Публичные интерфейсы и проверка зависимостей | Границы нужно поддерживать при каждом изменении |
| Нагрузка опроса растёт | Измерять задержки и число запросов; при подтверждённой проблеме добавить WebSocket | При нескольких экземплярах API потребуется согласовать рассылку событий |

## Условия пересмотра

Пересматривать решение, если нагрузочный тест не укладывается в цели после оптимизации запросов либо разные команды регулярно блокируют релизы друг друга. Первым кандидатом на отдельный сервис станет уведомление о новых сообщениях. Выделение выполняется постепенно по Strangler Fig: сохранить контракт, направить часть трафика в новый компонент, сравнить ошибки и задержки, предусмотреть возврат. Причину изменения зафиксировать в новом ADR; этот документ не переписывать задним числом.
